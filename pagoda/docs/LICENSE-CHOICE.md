# 开源协议选择：为什么是 AGPL-3.0

> 面向决策者和好奇的贡献者。一句话：**AGPL-3.0 让任何人都能自由使用、修改、
> 分发 pagoda，但任何人（包括 SGLang 这样的上游项目）都不能把 pagoda 的代码
> 直接抄进自己的闭源或宽松协议项目里。**

## 防的是什么，防不住的是什么

先说诚实的边界：

| 担心的事 | 协议能解决吗 |
| --- | --- |
| SGLang 把我们的 **Rust 源码**复制进他们的 Apache-2.0 仓库 | ✅ AGPL 与 Apache-2.0 单向不兼容：他们要么整体转 AGPL（不可能接受），要么不能用 |
| 云厂商魔改 pagoda 后**只提供 SaaS 服务**、不公开修改 | ✅ AGPL 的"网络交互即分发"条款专门堵这个漏洞（GPL 堵不住，AGPL 堵得住） |
| 别人**看了我们的设计文档**，自己重写一遍（思想抄袭） | ❌ 任何协议都防不住。架构思想不受版权保护 |
| 别人蹭 **pagoda 这个名字** | ❌ 协议管不着，需要商标（名字注册 + 商标政策） |

思想防不住，所以真正的护城河是：**迭代速度 + 文档/测试资产 + 品牌 + 社区**。
协议负责把"直接抄代码"这条路堵死。

## 候选方案对比

| 方案 | 是 OSI 开源 | 防抄进 SGLang | 防 SaaS 白嫖 | 采用门槛 | 结论 |
| --- | --- | --- | --- | --- | --- |
| Apache-2.0（原状） | ✅ | ❌ 随便抄 | ❌ | 低 | 否 |
| GPL-3.0 | ✅ | ✅ | ❌ SaaS 不分发即可规避 | 中 | 不够 |
| **AGPL-3.0** | ✅ | ✅ | ✅ | 中高 | **采用** |
| BUSL 1.1 | ❌（源码可见） | ✅ | ✅ | 高 | 备选，非"开源" |
| 双协议（AGPL + 商业授权） | ✅ | ✅ | ✅ | 中 | 未来可叠加 |

**"巧用"之处**：AGPL 是单向阀门——Apache-2.0 的代码（如 SGLang 的设计参考）
可以流入我们，我们的代码流不出去。同时保留了完整的开源四自由（使用/学习/
修改/分发），只是要求"分发时继续开放"。

未来如果要做商业版，作者（quantz8a）作为唯一版权持有者可以随时叠加商业授权
（双协议模式，MySQL/Qt 的先例）。**注意**：要保留这个权利，就需要贡献者签署 CLA
或在贡献指南中声明"贡献即授权持有者再授权"——详见贡献指南。

## 我们是干净的：与 SGLang 的版权关系

- pagoda 是**从零重写**（clean-room）：没有复制 SGLang 任何一行代码。
- 架构思想参考了 SGLang（Apache-2.0 允许学习与重实现），NOTICE 文件永久保留署名。
- 因此 pagoda 可自由选择协议，AGPL-3.0 的采用没有任何法律障碍。

## 实务清单

- `LICENSE`：AGPL-3.0 授权声明 + 官方全文 URL（本仓库离线编写；联网后应以
  `curl -sSL https://www.gnu.org/licenses/agpl-3.0.txt -o LICENSE` 替换为 verbatim 全文）。
- `NOTICE`：归属与血缘说明，永久保留。
- `Cargo.toml`：`license = "AGPL-3.0-only"`（crates.io / 工具链可机读）。
- 每个 `.rs` 文件头：`SPDX-License-Identifier: AGPL-3.0-only`（文件被单独复制时
  许可随之走）。
- 商标：另行考虑注册 "pagoda" 商标；协议不管名字。

## 公司环境提示

如果本项目未来涉及公司资产或在公司内部发布，请先过法务评审：
AGPL 对"内部使用"完全自由，对"对外分发/对外提供服务"才触发开放义务。
