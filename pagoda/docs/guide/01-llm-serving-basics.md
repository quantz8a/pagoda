# 01 · LLM 推理服务是什么

## 一句话总结

把一个大模型变成"很多人同时用、还要又快又便宜"的在线服务，就是 LLM 推理服务要解决的问题。

## 生活化类比

想象一家奶茶店：

- 模型本身 = 奶茶配方和原料（它是固定的）。
- **一次推理请求** = 一位顾客点单。
- **服务化** = 高峰期 100 位顾客同时点单，怎么安排柜台、怎么复用已经煮好的茶汤，
  让每个人都不用等太久，还不浪费原料。

SGLang、vLLM、pagoda 这类"推理引擎"就是这家奶茶店的**店长调度系统**。

## 它是怎么工作的

模型生成文字不是一个字"一下子"出来的，而是两个阶段：

```
prefill（预填）                decode（解码）
┌──────────────────┐         ┌───┐ ┌───┐ ┌───┐
│ 一口气读完整个    │ ──────▶ │ 生│ │ 生│ │ 生│ ... 直到结束
│ prompt 的每个字   │         │ 成│ │ 成│ │ 成│
└──────────────────┘         │ 1 │ │ 2 │ │ 3 │
                             └───┘ └───┘ └───┘
```

- **prefill**：把 prompt（比如 1000 个字）一次性读进去，建立"理解"。
  这一步计算量和 prompt 长度成正比，通常很快但很重。
- **decode**：一个字一个字往外蹦。每蹦一个字，都要把前面所有内容"再想一遍"。
  这一步决定了用户感受到的"打字速度"。

关键事实：decode 每生成一个字，都需要用到前面**所有字**的中间计算结果。
这些中间结果叫 **KV cache**（下一篇细讲）。显存里能放下多少 KV cache，
决定了一台机器能同时服务多少人——这就是为什么推理服务的核心难题是**内存管理**，
而不是算力本身。

## 为什么"省"比"快"更值钱

服务 1000 个用户时，如果 100 个人的 prompt 开头都一样（比如同一段 system prompt），
聪明的做法是：**相同的开头只算一次**。少算的部分就是纯利润。
pagoda 的 `/stats` 里有个指标叫 `compute_saved_tokens`，字面意思就是"省下来的算力"。

## 在 pagoda 里动手试试

```powershell
cd pagoda
# 同一个 prompt 重复 3 次，观察第二次起 prefill 被跳过
cargo run --offline --bin pagoda -- sample -p "SGLang is a serving framework" --max-tokens 40 --repeat 3
```

输出里 `prefix_hit` 一行会告诉你：后两次请求的开头部分完全没重新计算。

## 和 SGLang / vLLM 的对照

| 概念 | SGLang / vLLM | pagoda |
| --- | --- | --- |
| prefill / decode 两阶段 | ✅ | ✅（玩具模型，但流程一致） |
| KV cache 内存管理 | GPU 显存池 | 内存块池（`kv_cache.rs`） |
| 多人同时用（batching） | continuous batching | ✅ 同款简化版（第 7 篇） |
| 省算力（前缀复用） | RadixAttention / APC | ✅ 两种都实现了（第 3、4 篇） |

## 常见疑问

**Q：pagoda 里跑的是真模型吗？**
默认是一个确定性的"n-gram 玩具模型"，不联网、不需要 GPU，专门用来把整条服务链路跑通。
真实模型的对接点在姊妹 crate `pagoda-hf`（HuggingFace tokenizer + Candle 权重）。

**Q：为什么不直接用 PyTorch 跑个循环？**
能跑，但那只是"推理"，不是"推理服务"。服务化的价值全在调度、缓存、隔离这些"店长工作"上。
