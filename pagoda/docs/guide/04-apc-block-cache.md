# 04 · APC 块级哈希缓存

## 一句话总结

不走树，改查哈希表：把每**一整块** token 连同"前一块的指纹"一起算哈希，
查找时一块探测一次——这是 vLLM 的 Automatic Prefix Caching（APC）方案。

## 生活化类比

Radix 像逐页翻字典（第 3 篇），APC 像**文件去重系统**：
网盘上传文件时把文件切成固定大小的块，每块算个 MD5，已存在的块秒传、不重复存储。
区别是 KV 有顺序要求——第 5 块的内容只有在**前 4 块都一致**时才有意义。
所以 APC 用**链式哈希**：`第 n 块的指纹 = hash(第 n-1 块的指纹, 第 n 块的内容)`。
一旦前面任何一块不同，后面所有块的指纹全部不同，天然保证前缀语义。

## 它是怎么工作的

```
prompt = [t0..t3 | t4..t7 | t8 t9]     （块大小 4，最后一块不满）

h1 = hash(SEED, t0..t3)  ──▶ 查表：命中？→ 直接引用该物理块
h2 = hash(h1,   t4..t7)  ──▶ 查表：命中？→ 直接引用
h3 = 不算                 ──▶ 尾部不满一块，留给正常 prefill
```

- **查找**：O(块数) 次哈希探测，比逐 token 走树快得多。
- **淘汰**：直接以块为粒度，LRU 踢掉最久没用的块，干脆利落。
- **代价**：块粒度——最后不满一块的部分（上面例子的 `t8 t9`）不能复用。

### 和 Radix 的取舍

| | Radix（SGLang） | APC（vLLM） |
| --- | --- | --- |
| 复用粒度 | token 级，尾巴也能复用 | 块级，尾巴不足一块不复用 |
| 查找成本 | O(前缀 token 数)，逐节点走 | O(块数) 次哈希探测 |
| 淘汰粒度 | 叶子节点（可能牵连半块） | 整块，简单直接 |
| 内存元数据 | 每 token 一个树节点 | 每块一条表项，极省 |

真实系统里两者命中率差距通常只有几个百分点，但 APC 的实现和运维简单得多。

## 在 pagoda 里动手试试

```rust
use pagoda::{CacheBackend, EngineConfig, ToyEngine};

let mut engine = ToyEngine::toy(EngineConfig {
    cache_backend: CacheBackend::Apc,   // 一行切换
    block_size: 16,
    ..EngineConfig::default()
});
```

`GET /stats` 里 `apc_blocks` / `apc_hit_tokens` 观察它的工作；
`compute_saved_tokens` 对两种后端统一计账，可以直接对比。

集成测试 `tests/apc_tests.rs` 里有完整的行为规格：全块命中、尾部不复用、
首块分叉全链失效、压力淘汰、两种后端输出一致性。

## 和 vLLM 的对照

| 机制 | vLLM APC | pagoda `apc.rs` |
| --- | --- | --- |
| 链式块哈希 | ✅（含 token 内容 + 父哈希） | ✅ splitmix64 混合 |
| 只缓存满块 | ✅ | ✅ |
| 块粒度 LRU 淘汰 | ✅ | ✅ |
| 缓存持有基础引用 | ✅ | ✅ 每索引块一份 |

## 常见疑问

**Q：哈希冲突怎么办？两块不同的内容算出同一个指纹岂不乱套？**
理论上可能，实践上 64 位链式哈希的碰撞概率约等于陨石砸中机房。
vLLM 生产环境就这么跑。要绝对保险可以加内容校验，代价是每次命中多一次逐 token 比较。

**Q：什么时候选 APC 而不是 radix？**
prompt 普遍很长、块大、QPS 高：APC 的 O(块数) 查找优势明显。
短前缀、大量"尾巴也对得上"的场景：radix 更省算力。用 pagoda 两种都跑一遍对比就行。
