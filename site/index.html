why it wins

精度吃亏，还是更快

GPU 侧 pagoda 跑全 f32，官方 Python 自动 fp16（带宽和算量减半）。小模型 + 单请求场景下，Python 的逐层派发和 autocast 上下文切换吃掉了 fp16 的理论红利。

determinism

逐位确定，进 CI

e2e 断言两次 decide 的概率 to_bits() 完全相等，每次提交都拦非确定性改动。风控、路由这类阈值敏感场景，跨硬件可复现是硬保障。

诚实清单

差距也摆在这

CPU 延迟慢 2.25 倍——torch 的 oneDNN/MKL 在 CPU 上仍是业界最强，路线图是 BLAS / int8 内核；批量决策暂缺（当前逐请求）；只做推理、不带训练侧，刻意取舍。

Why · 它到底做了什么

跟别的实现，差在哪

一句话：整合各家所长 + Rust 的标准库 + 几个 agent 场景原语。下面每条都对应代码，不是口号。

∅
no deps

零第三方依赖

只依赖 std。没有 tokenizers、没有 candle、没有 CUDA，cargo test --offline 一次过 87 个测试。

内网 / 金融 / 政务 / 涉密环境都能直接 build。
⇄
radix vs apc

两种前缀缓存都能切

radix 和 APC 塞进同一个引擎，EngineConfig.cache_backend 一行切换，共用同一套 KV 池和指标。

想比 radix 和 vLLM 的 APC，切个枚举就行。
⑂
checkpoint

KV checkpoint

把共享的 system prompt / 历史对话钉住，后面随便开分支，前缀 100% 命中，不会被 LRU 挤掉。

SGLang 和 vLLM 现在都没有这个原语。
Σ
kv session

增量 KV 会话

prompt 只预填充一次，之后每步只喂新 token。16 步生成从 216 个 token 降到 21 个。

每个 token 只算一次，出错自动回退到全量重放。
⫽
batched decode

批量解码

把刚好缺一个 token 的会话拼成 [B,1] 一次前向。实测调用次数降 6.24×，框架开销场景吞吐 +40%。

decode_batch_factor 能在 /stats 里看到。
⋈
tensor grafting

张量嫁接

跑完的会话把 KV 张量存进 vault，新请求前缀一样就直接切片复用。134 token 的 warm prefill 可以归零。

共享系统提示从「少算」变成「不算」。
◇
grammar

零依赖约束解码

regex + JSON 两套 grammar 手写，接 logit mask，-inf 也正确处理。不用拖 Outlines/xgrammar。

边缘和嵌入式也能做结构化输出。
¥
metrics

能看省了多少算力

/stats 直接给 compute_saved_tokens、prefill_skip_ratio、avg_forward_per_output_token、kv_utilization。

不用自己从访问日志反推，接口里就有。
⚓
co-deploy

共部署网关

一条脚本起两个进程：pagoda 守门（健康检查、指标、checkpoint），生成请求透传给上游引擎。

现有部署不用改，接上一层控制面即可。

诚实地说，它还没做到的事

  • 主 crate 跑的是确定性的 n-gram 模型：链路是真的，算力是模拟的。真权重在 pagoda-hf（HF tokenizer + Candle），要联网。
  • KV 里存的是 token id 不是张量：分页 / 引用计数 / COW 的语义是真的，但没有真的接 GPU 张量。会话内已经做到张量级，跨请求的复用标在 P3。
  • grammar 是字节级，只在字节 tokenizer 上合法；引擎会直接拒绝误用。

和上游 Rust 线的关系
upstream · rust/sglang-mm

多模态预处理（pyo3）

MmFamilyProcessor + pipeline 分发 + common/{resize,decode,token_layout}；InternVL 是第一个 family。

和这里的关系：同一个“用 Rust 重写 SGLang”方向下的不同切片，一个做预处理扩展，一个做运行时。
upstream · rust/sglang-server

Rust 服务端 / 路由

和官方 sglang-router 同思路：Rust 控制面 + Python worker，目标是 scheduler / api server / prefix tree 重写。

和这里的关系：网关控制面同源，这里额外把 checkpoint、指标、准入做了进去。
Laya · System 1

只判断，不生成

Laya 是决策模型：给一段现场和几个带类型的问题，一次前向返回答案 + 校准概率，不吐 token，所以没有幻觉可捉。

一个类比

分诊台护士 vs 主治医生

分诊台 30 秒判断“挂哪个科、急不急”——快、便宜；医生慢慢问诊。医院不会让医生干分诊，agent 也不该让 GPT 去判断“这封邮件转给哪个组”。

它怎么做

一次非自回归前向

ModernBERT 编码器（双向注意，28 层）→ 决策头（只看 [MASK] 哨兵位置）→ 每选项一个分数 → softmax → 温度校准。

choice（N 选一）· score（有序打分）· noul（是否）
题型 01

choice

N 选一，返回标签 + 分布。例如 department=billing，confidence 0.927。

题型 02

score

有序打分，输出期望档位。例如 urgency=1.772（满分 2，blocking 档）。

题型 03

noul

是否题，输出“成立”的概率。例如 churn_risk=0.879。

为什么零幻觉

输出被题型框死

choice / score / noul 三种题型 + softmax 分布，不生成一句话，判断类任务上没有自由文本幻觉可产生。

蒸什么

蒸「诚实的概率」

用 Laya 校准后的概率做软标签，学生去拟合这个分布，而不是抄 one-hot 答案。

边界先讲清楚

  • “零幻觉”只在判断类任务上成立：不生成开放文本，就没有自由文本幻觉。
  • 学生继承的是「题型 + 概率」的约束；开放生成不归这个框架管。

网关做什么

按概率设阈值

部署形态

边端 CPU，几十毫秒

训练时用 Laya 老师出软标签；生产跑蒸馏后的小模型（几十 MB），不占 GPU，判定概率直接当阈值和置信度。

从大模型到小模型 · 闭环

大模型打头，Laya 在中间，小模型收尾

第一层是生成层：radix 前缀缓存 + 连续批调度负责大模型吞吐。中间不是 RLHF 的“讨好人奖励”，而是 Laya 的校准概率。

传统 RLHF 的坑

奖励“像人”，不是“真实”

用人类偏好奖励训练，模型会学成“说你想听的”那种谄媚；遇到不确定就更倾向编造，幻觉跟着来。

Laya 的解法

奖励 = 诚实

严格适当评分规则（RLCD）下，只有报真实概率才拿满分；题型只有 choice/score/noul + 概率，长不出自由文本。

关键词：radix / 连续批调度 / 校准概率

  • 生成层的吞吐交给 radix 前缀缓存和连续批调度，不会因为蒸馏被阉割。
  • 蒸馏的监督信号是概率分布，不是“是否讨人喜欢”，所以小模型不谄媚、判断上不幻觉。
