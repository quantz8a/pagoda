1 · Prefix sticky 路由

文件 pagoda/src/pd.rs · PR #15 · 轴 TTFTToken/Watt

相同 prompt 先走 FNV-1a sticky，命中后 record 只 bump routed、跳过字符 trie 增长。冷路径 RR 从 worker 0 起；/stats 暴露 sticky_hits / upstream_cache_hit_ratio。

代理层对「共享 system prompt 反复打同一 decode worker」的路径从 O(字符数) 降到 O(1) hash；长 trunk 越明显。

对照 · 延迟分布

Source: local release microbench · Apple Silicon · 2026-10-11 · n=50 000

prompt = 2320 bytes（「You are a helpful assistant. 」×80）。sticky 含 pick+record；prefix 为扩展串上的纯 pick trie walk。

2 · Qwen3.5 GDN 热路径

模块 pagoda-hf/src/qwen3_5/ · PR #16 · 轴 TTFTToken/Watt

改了什么

  • recurrent_gated_delta_rule：连续切片访问；decay+kv_mem 一趟；S+=k⊗δ 与输出 matvec 融合
  • q/k/δ/kv_mem scratch 跨 head/time 复用，去掉 per-token to_vec
  • causal conv：copy_within 原地滚环；prefill 带回最终 ring 供 decode
  • Dense gemm：4-wide 手写累加（decode seq=1）
单层 Qwen3.8 形状（hv=48, dk=dv=128）release：0.211 ms/step · 4736 steps/s。64 层仅 GDN 部分约 ~13.5 ms/token（不含 full-attn / MLP / 量化反解）。

复现

# after PR #16 lands: cd pagoda-hf cargo test --release --offline --lib decode_throughput_qwen38_shaped cargo run --release --offline --example bench_gdn_decode # → ms_per_step≈0.21 steps_per_s≈4700 (hv=48 dk=dv=128)

护栏：debug 下 32 step < 5 s。GPU/FLA 见 #18。

3 · mlx-http 适配器

文件 pagoda-hf/src/mlx_engine.rs · PR #16 · 轴 Useful LifeTTFT

  • Phase 1：每步 max_tokens=1 → 稀疏有限 logits（floor + peak），满足 Engine 对 NaN/Inf 的拒绝
  • 会话内 fill_sparse_logits 复用 ~248 k×f32 缓冲，避免每 decode 步重新 vec![floor; vocab]
  • /stats 附带 upstream_prompt_tokens / upstream_cached_tokens / mlx_remote_steps
下一刀最大收益：去掉 decode→text→encode 往返，直接传 token ids（#17）。

方法学备注

  • 微基准在 Apple Silicon、Rust release、cargo --offline 下采集；跨机数字会漂移，比例更稳。
  • Sticky 5.9× 是路由层相对字符 trie walk 的加速，不是端到端 TTFT；端到端还取决于上游 KV 命中（由 upstream_cache_hit_ratio 观测）。
  • GDN 数字是单层 CPU 参考核；完整 27B 仍走 mlx-serve Metal，本核是 Candle 混合栈与正确性基线。
